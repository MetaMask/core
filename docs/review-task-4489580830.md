The Core half of that comment is the last sentence. Mobile was deciding the withdrawal venue itself: `hyperliquid` and `lighter` stayed themselves, and `aggregated`, a missing provider, or anything else became `hyperliquid`. That map is provider-routing policy. It ignores a saved `defaultProvider`, and it ignores the rule that an aggregated withdrawal with several venues and no `providerId` is refused instead of signed on Hyperliquid.

The Core PR makes `@metamask/perps-controller` the owner of that decision. A public query reports the venue `withdraw` will actually sign on, or the same `PROVIDER_ROUTE_REQUIRED` refusal `withdraw` returns. Mobile then asks Core, checks account support for that venue, and deletes its own map. Order and market support checks keep passing their own explicit `providerId`. No-argument `getAccountSupport()` stays a read of the routing default, including when `withdraw` would refuse.

The in-flight retirement (stop a pending Lighter result from opening a Hyperliquid withdrawal, plus a deferred provider-switch regression) stays a Mobile change. It is not part of this PR. Current Mobile `faef6a3f3c8` calls `checkAccountSupport()` with no venue from `handleWithdraw`, so re-read that call site before describing it. Do not edit metamask-mobile here.

## Contract the query must keep

`resolveWithdrawalRoute(params?)` answers "which venue will this `withdraw` sign on?" for the same optional `providerId`.

```typescript
export type ResolveWithdrawalRouteParams = {
  providerId?: PerpsProviderType;
};

export type WithdrawalRoute =
  | { status: 'resolved'; providerId: PerpsProviderType }
  | {
      status: 'route_required';
      error: Extract<PerpsErrorCode, 'PROVIDER_ROUTE_REQUIRED'>;
    };
```

Behavior, matching `473ae0148c0`:

1. Call `#getUnroutedAggregatedWriteRefusal` before waiting for the provider, and again after `#getActiveProviderWhenReady`. A cold start can migrate a direct session to aggregated. Either refusal returns `{ status: 'route_required', error }` and does not throw.
2. A direct provider whose explicit `providerId` is a different venue throws `PROVIDER_NOT_FOUND`, via `#hasConflictingProviderRoute`. `withdraw` on this branch throws that same error before withdrawal tracking or signing. `25.0.0` does not. The port includes that `withdraw` guard, so the query and `withdraw` still agree.
3. Aggregated mode with an explicit id that is not registered throws `PROVIDER_NOT_FOUND` (`hasProvider`). Aggregated mode with an explicit registered id, or with one registered venue and no id, returns `{ status: 'resolved', providerId }` from `getWriteProviderId`.
4. A direct provider with no conflicting id returns that provider's id (`#getDirectProviderId`, otherwise `protocolId`).

Do not report route-required by throwing. Mobile's account-support read catches every error and treats it as `{ isSupported: true }`. A thrown refusal would let the withdrawal continue.

Do not change no-argument `getAccountSupport()`. On an aggregated provider it still follows `#getProviderOrDefault`, so it checks the routing default even when `withdraw` would refuse. That split is why the new method exists. Order and market checks pass an explicit execution `providerId` and must keep doing so.

`getWriteProviderId` is not this query. It returns the routing default when `providerId` is omitted, including when several venues are registered and `withdraw` refuses. On `25.0.0`, `AccountService` stamps that helper onto the withdrawal record only after `withdraw` has already allowed the write. Leave that stamping alone.

## What 25.0.0 changed around withdrawals

Re-read these on current `main` before copying the branch forward. They do not replace the query.

- `getWithdrawalRoutes` returns every active venue's routes, each tagged with `providerId` ([#11461](https://github.com/MetaMask/core/pull/11461)). The first USDC route is registration order, not the venue `withdraw` signs on. Deposits select a route in `DepositService.#selectDepositRoute` and fail closed. Withdrawals have no equivalent selector. Do not implement `resolveWithdrawalRoute` by scanning `getWithdrawalRoutes()`.
- Combined `withdrawableBalance` spans venues. It is not the limit one venue will enforce on a withdrawal. The support check stays per venue.
- `AggregatedPerpsProvider.withdraw` still does `this.#getProviderOrDefault(params.providerId)`.

The signing rules in the contract above are the ones to preserve. The rebase risk is file overlap in `PerpsController.ts`, the changelog, the README, and `PerpsController.operations.test.ts`, plus the missing pre-tracking `PROVIDER_NOT_FOUND` guard on `25.0.0`.

## What Mobile duplicates today

`resolveWithdrawalProviderId` in `app/components/UI/Perps/hooks/usePerpsHomeActions.ts` maps the active provider mode onto a concrete venue and passes that id into `checkAccountSupport`:

- `hyperliquid` or `lighter` → that id
- `aggregated`, `undefined`, or anything else → `hyperliquid`

`handleWithdraw` also passes that function as `watchActiveProvider`. `PerpsWithdrawView` then calls `controller.withdraw` with no `providerId`.

That map is routing policy. It does not follow `defaultProvider` / `setDefaultProvider`, and it does not follow the multi-venue refusal. A saved Lighter default, or an aggregated session with both venues registered, still produces a Hyperliquid support check.

## Contract to match

Trace `PerpsController.withdraw` and reuse it. Do not add a parallel map from `activeProvider` to `hyperliquid`.

Current resolution, from `withdraw`, `#getUnroutedAggregatedWriteRefusal`, and `AggregatedPerpsProvider.withdraw` / `#getProviderOrDefault`:

1. **Direct mode** (`activeProvider` is `hyperliquid` or `lighter`). An omitted `providerId` signs on that provider. An explicit id that is not that provider is rejected by `#hasConflictingProviderRoute` as `PROVIDER_NOT_FOUND`.
2. **Aggregated, one registered venue.** An omitted `providerId` is allowed and reaches that venue, including the existing in-memory Hyperliquid fallback when the saved default is unavailable. One-venue membership is not known before initialization; `withdraw` checks again after `#getActiveProviderWhenReady` because a cold start can migrate direct state to aggregated.
3. **Aggregated, more than one registered venue, omitted `providerId`.** `withdraw` returns `{ success: false, error: PROVIDER_ROUTE_REQUIRED }`. It does not fall through to `defaultProvider` or to Hyperliquid. The support query must report that same refusal. It must not return Hyperliquid's `PerpsAccountSupport`.
4. **Explicit `providerId` in aggregated mode.** The write reaches that registered venue. Unknown ids throw `PROVIDER_NOT_FOUND`, matching `#getProviderOrDefault`.

`effectiveProvider` is the live venue for implicit reads and streams. It is not the withdrawal venue when several venues are registered. `getAccountSupport()` with no args still routes an aggregated provider through `#getProviderOrDefault`, so a no-arg support read checks the routing default even when `withdraw` would refuse. That split is why a new query is required. Do not "fix" it by changing no-arg `getAccountSupport`.

Order and market flows pass an explicit execution `providerId` and must keep doing so. A withdrawal query must not change those reads.

## Required behavior

Add one public controller method that answers "which venue will this `withdraw` sign on?" for the same optional `providerId` `withdraw` accepts.

- Wait for provider readiness the same way `withdraw` does, and apply the refusal both before and after that wait.
- Return a typed result. Two outcomes are required: a resolved `PerpsProviderType`, and route-required. Match existing error-code naming (`PROVIDER_ROUTE_REQUIRED`) rather than inventing a second code.
- Do not signal route-required by throwing. Mobile's `readAccountSupport` catches every error and fails open as `{ isSupported: true }`. A thrown refusal would let the withdrawal continue. `PROVIDER_NOT_FOUND` for a conflicting or unknown explicit id can keep the existing throw, because that is already how `getAccountSupport` and `#getProviderOrDefault` behave.
- Expose the method the same way `getAccountSupport` is exposed: `MESSENGER_EXPOSED_METHODS`, a `PerpsController:*` action type in `PerpsController-method-action-types.ts`, and an explicit export from `src/index.ts` (no barrel `export *`).
- Document it on the controller method. Mention the withdrawal use in `packages/perps-controller/README.md` next to the existing multi-provider `withdraw` paragraph, in a few sentences.
- Add an Unreleased changelog entry under Added. This is a new public method. It is not breaking unless you also change `getAccountSupport`, `withdraw`, or `PerpsAccountSupport`. Do not do that.

Suggested shape, to be adjusted to the code you find:

```typescript
export type WithdrawalRoute =
  | { status: 'resolved'; providerId: PerpsProviderType }
  | { status: 'route_required'; error: typeof PERPS_ERROR_CODES.PROVIDER_ROUTE_REQUIRED };

resolveWithdrawalRoute(params?: { providerId?: PerpsProviderType }): Promise<WithdrawalRoute>;
```

Use a name that reads as the venue `withdraw` will use. Keep the method on `PerpsController`. Do not make Mobile depend on `AggregatedPerpsProvider.getWriteProviderId`; that helper returns the routing default even when `withdraw` refuses.
